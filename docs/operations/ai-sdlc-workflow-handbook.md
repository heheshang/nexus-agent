# AI-SDLC 流程手册

> 叙事版。**判据在 `.cursor/rules/`**，本手册解释「为什么这样设计」和「怎么走一遍」。
> 两者冲突时以 `.cursor/rules/` 为准。

---

## 一句话

AI-SDLC 不是「让 AI 写代码更快」，而是**让 AI 只在已经想清楚的事情上动手**。

它的核心命题是：**AI 执行规格明确的契约是确定性的**。
规格含糊时，AI 的产出会发散 —— 而且发散得比人更快、更自信、更难发现。
所以流程的重点不在「写代码」这一步，而在**写代码之前的每一个决定**。

---

## 全景：九个阶段

```
S0 需求捕获
   │
S1 分层判定 ──── 有分歧？ → Tier 1 RFC
   │              多任务？ → Tier 2 Spec
   │              否则     → Tier 3 Task
S2 产出物编写
   │
S3 DoR 门禁 ──── 不过？ → 退回 S2 澄清（不开工）
   │
S4 实现
   │
S5 三层验证
   │
S6 评审 ──────── changes-requested？ → 回 S4（最多 2 轮）
   │
S7 合并与交付
   │
S8 部署与运维
   │
S9 度量与校准 ── 反馈到 S3 的门禁严重度与 S1 的复杂度打分
```

完整阶段表（进入条件 / 产出物 / 退出条件 / 失败处理）见
`.cursor/rules/ai-sdlc-workflow.mdc` §2。

**两道硬边界**：

- **S3 → S4**：DoR 判定必须先于任何代码写入。
- **S6 → S7**：评审必须先于合并。

这两道边界防的是两类失败：
前者防「**交付了错误的东西**」，后者防「**没人看过的变更进入 `main`**」。

## 每个阶段在防什么

### S1 分层 —— 防「用战术掩盖战略」

一个改动到底该是任务、规格还是决策文档？
判据不是「大小」，而是**分歧的存在**：

> 存在合理工程师会就正确做法产生分歧 → 这是决策问题（RFC）。
> 一个特性能拆成多个任务 → 这是契约问题（Spec）。
> 否则 → 这是交付问题（Task）。

**层级独立可用** —— 不必每次都从 RFC 走下来。
绝大多数日常功能工作直接从 Task 层进入。

### S2 产出物 —— 防「计划写在脑子里」

产出物不是为了文档化，是为了**让下一个接手的人（可能是三个月后的你）能复核**。
判断标准很简单：**这份产出物里的每一句话，别人能不能独立验证？**

### S3 DoR —— 防「每个环节都觉得自己做对了」

这是 AI-SDLC 最容易被低估的一道门。

典型失效链条：

```
AC 含糊  →  实现跑偏  →  评审按同一条含糊 AC 判过  →  合并后才发现交付的是错的东西
```

注意链子的第三步：**评审也是被含糊 AC 拖累的**。
评审者面对「改善用户体验」这样的 AC，只能凭自己的想象补全标准 ——
于是评审通过了，但通过的是一个**假的标准**。

七项门禁各自抓一种独立的失效模式（详见 `.cursor/rules/ai-sdlc-dor-gate.mdc` §2）。
**默认严重度全是 Block** —— 这不是官僚，是默认值应该保守。

### S4 实现 —— 防「顺手把决策做了」

实现阶段最常见的越权是**在代码里顺手定一个决策**：
「这里超时了，那就当可重试吧」——
但「超时 = 结果未知 = 禁止自动重试」是**架构文档已定稿的条款**，
不是实现细节。

所以规则是：**要么改架构文档（走决策），要么按架构文档实现，没有第三条路。**

### S5 三层验证 —— 防「测试测了个寂寞」

三层各管一件事：

| 层 | 断言什么 | 手段 |
|---|---|---|
| 类型层 | 写错的代码**编译不过** | `trybuild` 负向测试 |
| 结构层 | 依赖方向、无环、`sqlx` 收敛 | 架构测试 / 源码扫描 |
| 行为层 | 语义不变量 | 集成 / 不变量测试 |

**结构层是本项目的特色** —— 它能拦住**静默的行为退化**。
例如把 `std::sync::Mutex` 换成 `tokio::sync::Mutex`：
编译通过、测试可能也过，但丢掉了「编译器强制你不在持锁时 await」的保护。
这类退化只能靠**扫描源码的结构层断言**钉住。

而结构层扫描**必须剥离注释** —— 文档注释里解释「为什么不用 X」是正常文字，
不是实际使用。这一点在 NEX-18 里踩过（见该任务的「实现过程中的发现」§5）。

### S6 评审 —— 防「评审者被污染」

三件事：

1. **AI 作者的改动需要额外一名评审** —— 人的注意力是最贵的资源，
   不该浪费在「让 AI 觉得自己被审过了」上。
2. **评审者只评审不修复** —— 一旦开始改代码，独立性就没了，
   而且改动绕过了 DoR 与门禁。
3. **迭代上限 2 轮** —— 第 2 轮还有 critical/major 就交人工，
   而不是无限循环。

### S7 合并 —— 防「历史被搅乱」

始终 rebase 到 `main`，绝不把 `main` merge 进来。
线性历史让 bisect、让 review、让「哪个提交引入的」这些问题都变得可回答。

### S8–S9 运维与度量 —— 防「交付即遗忘」

S9 的度量**不是为了打分**，是为了**校准流程参数**：

- 某门禁误报率高 → 它的严重度该从 Block 降为 Warn（需 RFC 修订）。
- 集成测试经常被跳过 → 门禁的断言下限该上调。

校准的产物是**规则修订**，不是**单次豁免**。

## 决策者在哪里

AI-SDLC 叫自己「决策引擎」，因为**决策权始终在人手里**。

三分类（详见 `.cursor/rules/ai-sdlc-decision-authority.mdc` §2）：

| 类 | 场景 | 代理怎么做 |
|---|---|---|
| **decide-and-proceed** | 可低成本回滚、影响面小 | 自己定，记录下来，立刻应用 |
| **timeboxed** | 难回滚、影响面大、削弱控制 | 记录决策 + 时间盒 + 无人干预时的回退方案 |
| **operator-only** | 法律、money、账号凭据 | **绝不自己定**。搁置这一个任务，其余继续 |

**OQ 解决权专属操作者。** 代理可以**发现**开放问题、**登记**它、
**呈现选项** —— 但不能**消解**它。

**Away rule**：操作者不在场时不发起阻塞性提问。
这听起来像放弃，实际是**保护交付连续性** —— 一个永远在等确认的代理，
比一个做出明确假设并继续的代理更糟。

**Velocity**：任何拒绝都必须给出**代理可自行执行的下一步**。
拒绝若终结任务，就等于把成本转嫁给了人，却没有产出任何东西。

## 在本仓库怎么落地

| AI-SDLC 概念 | 本仓库载体 |
|---|---|
| Tier 1 · RFC | `docs/rfcs/NEX-RFC-<n> - <slug>.md` |
| Tier 2 · Spec | `docs/specs/<feature>/{spec.md,tasks.md,contracts/}` |
| Tier 3 · Task | `backlog/tasks/NEX-<n> - <slug>.md` |
| Pipeline | 本仓库未接入管道 —— 用「手写流程 + CI 门禁」等价实现 |
| QualityGate | `.github/workflows/ci.yml` + `scripts/check-*.sh` |
| Provenance | 提交信息的 `Co-Authored-By` 尾注 |
| Audit trail | 任务文件的 DoR 判定段落 + PR 描述 + CI 日志 + git 历史 |
| AutonomyPolicy | `.cursor/rules/ai-sdlc-autonomy.mdc` §1–§4 |

**三层产出的门禁**：

| 层 | 门禁 | 拦什么 |
|---|---|---|
| Tier 1 · RFC | 人工评审 | OQ 被代理消解 |
| Tier 2 · Spec | `bash scripts/check-specs.sh` | 三件套缺失；`tasks.md` ↔ backlog 漂移；契约引用不存在的测试；错误码白名单漂移 |
| Tier 3 · Task | `bash scripts/check-backlog.sh` | 任务重复归档；完成态未标记 |
| 规则层 | `bash scripts/check-rules.sh` | 规则引用不存在的路径；`AGENTS.md` 清单漂移 |

**注意 `check-specs.sh` 规则 3 的意义**：
`contracts/invariants.json` 里每条不变量都指着一个**真实的测试名**，
门禁会核对该测试在对应文件里**确实存在**。
这是「防伪」—— 声称「某测试验证了这条不变量」但那个测试根本不存在时，
契约就是**空头支票**。规则文件里如果只有散文判据，同样会退化成空头支票 ——
这就是 `check-rules.sh` 存在的理由。

**未接入管道的事实要记住**：AI-SDLC 的 DoR 由 `cli-dor-check.mjs` 执行（Stage A 脚本 + Stage B LLM）。
本仓库是**手工执行**（代理逐项核对 + 判定记录落到任务文件）。
若将来 `ai-sdlc init` 接入，**`.ai-sdlc/` 的配置优先于本手册与规则文件**。

## 一张自检表

开始任何工作前，问自己：

- [ ] 这是 Task 层的工作吗？还是需要先出 RFC / Spec？
- [ ] 产出物的每条 AC 都能二元判定吗？
- [ ] 我依赖的架构条款**已定稿**吗？
- [ ] 这次改动触及契约吗？触及哪几项？
- [ ] 有开放问题吗？是阻塞性的吗？
- [ ] 决策是三分类里的哪一类？我有权自己定吗？
- [ ] 新代码落在三层验证的哪一层？
- [ ] 提交前六道门禁绿了吗？任务号真实存在吗？
