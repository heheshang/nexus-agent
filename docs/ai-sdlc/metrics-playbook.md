# 度量与校准操作手册

> **判据在 `.cursor/rules/ai-sdlc-observability.mdc`**。本手册讲**每个指标的分母是什么**、
> **快照怎么写**、**校准怎么落地**。两者冲突时以规则文件为准。

---

## 0. 度量是为了**校准流程**，不是为了排名

这是 S9 存在的唯一理由。

```
观测到某个现象 → 判断是流程参数的问题 → 修订规则（需 RFC） → 下个周期验证效果
```

**校准的产物是规则修订，不是单次豁免。**

> 用度量来「证明工作做得好」是误用 ——
> 门禁全绿不等于做的是正确的事，门禁全红也不等于做得差。

---

## 1. 五类指标 —— 每个都写明分母

**分母缺失的指标不允许上线。** 上游把这条定为 `advisory`（记录但不拦截），
本仓库把它当成**写文档时的硬要求**：下表里每一行都有分母。

### 1.1 任务有效性

| 指标 | 分子 | **分母** | 数据来源 |
|---|---|---|---|
| DoR 通过率 | DoR 判定为 `pass` 的任务数 | **本次评估的全部任务数**（含 `needs-clarification` 与 `blocked`） | 任务文件的 `## DoR 判定` 段落 |
| 首次通过率 | 一次就 `pass` 的任务数 | **本次评估的全部任务数** | 同上 |
| 返工次数 | 实现阶段回到 S4 的次数 | **进入实现的任务数** | 提交历史 / PR 评论 |
| 评审轮次 | 每个 PR 的评审轮数 | **已评审的 PR 数** | PR 评审记录 |
| 评审发现的 AC 覆盖率 | 被 finding 指向的 AC 数 | **该 PR 的 AC 总数** | 评审结论的 `acCoverage` |

> **分母为什么重要**：「DoR 通过率 90%」——
> 分母是全部任务，还是**只算被门禁检查过的**任务？
> 如果只算「代理觉得该做的任务」，这个数字永远是 100%，毫无信息量。

### 1.2 人机协作指标

| 指标 | 分子 | **分母** | 数据来源 |
|---|---|---|---|
| 阻塞等待时长 | 从提出阻塞性提问到收到答复的时长之和 | **阻塞性提问的次数**（不是任务数） | 任务文件 / PR 评论 |
| 审批轮次 | 每个 PR 的审批次数 | **已合并的 PR 数** | PR 记录 |
| 决策疲劳信号 | 同一操作者单日处理的决策请求数 | **全部决策请求** | 人工记录 |
| 假设显式化率 | 记录了显式假设的非阻塞性问题数 | **非阻塞性问题总数** | 任务文件的决策记录段 |

> **决策疲劳是 AI-SDLC 明确建模的**（RFC-0035 §2.2）：
> 决策超载会烧掉信任，而信任一旦烧掉，整条管道的价值归零。
> 这个指标**不是**用来考核人的 —— 它是流程设计的输入。

### 1.3 代码质量

| 指标 | 分子 | **分母** | 数据来源 |
|---|---|---|---|
| 门禁通过率 | 首次 CI 即通过的任务数 | **进入 CI 的任务数** | CI 日志 |
| clippy 告警数 | 告警条数 | — （绝对值） | CI 日志 |
| 测试覆盖率 | 被覆盖的可执行行 | **可执行行总数** | 覆盖率报告 |
| 集成测试实际运行率 | 实际运行的集成测试数 | **集成测试总数** | CI 解析测试输出 |
| 变异测试存活率 | 变异后仍然变绿的变异体数 | **变异体总数** | 变异测试报告 |

> **集成测试实际运行率是本仓库特有的**：
> 集成测试的判据是 `DATABASE_URL` 是否存在，不存在时**全部跳过但在摘要里显示 `passed`**。
> 「CI 全绿」**不能**证明「集成测试跑了」—— CI 额外解析输出断言各套件的实际运行数量。

### 1.4 经济效率

| 指标 | 分子 | **分母** | 数据来源 |
|---|---|---|---|
| token 消耗 | 周期内总 token | — （绝对值） | ⚠️ **本仓库未接入计量** |
| 构建时长 | CI 构建耗时 | **CI 运行次数** | CI 日志 |
| 重试次数 | 上游重试发生次数 | **上游调用次数** | 应用日志 |
| 评审成本 | 评审轮数 × 每轮评审量 | **已评审的 PR 数** | PR 记录 |

> **本仓库目前不按 agent 维度核算 token 消耗** ——
> 这需要 usage ledger（RFC-0050）。缺失的这一格在
> `docs/ai-sdlc/coverage-matrix.md` §3 `usage-ledger-model-routing.md` 行标为「部分适配」。

### 1.5 自治轨迹

| 指标 | 分子 | **分母** | 数据来源 |
|---|---|---|---|
| 各等级任务分布 | 落在每个自治等级的任务数 | **全部任务数** | 任务文件的路由记录 |
| 降级触发次数 | 触发降级的事件数 | — （绝对值） | 任务文件 / PR 记录 |
| 冷却期任务占比 | 处于冷却期的任务数 | **全部任务数** | 任务文件 |
| 越权事件 | 代理在无批准下执行 operator-only 动作的次数 | — （绝对值，**目标恒为 0**） | 审计记录 |

## 2. 指标的三条禁令

| 禁令 | 理由 |
|---|---|
| **不得用于个人绩效评估** | 按作者统计的指标只用于**模式检测**（`ai-sdlc-dor-gate.mdc` §7） |
| **不得被用来「证明工作做得好」** | 门禁全绿 ≠ 做的是正确的事 |
| **不得有「没有分母」的指标** | 缺分母的数字无法比较，也无法跨周期比较 |

## 3. 指标快照模板

## 口径说明

- 统计周期：<起止日期>
- 统计范围：<哪些分支 / 哪些任务类型 / 是否含未合并任务>
- **分母定义**：<逐条列出本快照用到的分母>
- 数据来源：<CI 日志 / PR 记录 / 任务文件 / 人工记录>

## 一、任务有效性

## 4. 校准流程

### 4.1 观测 → 判断 → 修订

| 观测到的 | 调整 | 修订载体 |
|---|---|---|
| DoR 某门禁**误报率**高 | 该门禁严重度从 `Block` 降为 `Warn` | **RFC 修订**（严重度是门禁的属性，不能随手改） |
| 某门禁**漏报**（放过坏任务） | 该门禁严重度从 `Warn` 升为 `Block` | RFC 修订 |
| 某类返工反复发生 | 该类改动的复杂度打分**上调** → 路由到更严的策略 | `ai-sdlc-autonomy.mdc` §2.1 的打分表修订 |
| 评审轮次长期为 1 | 评审 remit 可收紧（更多 findings 阈值） | `ai-sdlc-quality-gates.mdc` §4.2 修订 |
| 集成测试频繁被跳过 | 门禁第 9 条的断言下限需上调 | `.github/workflows/ci.yml` 修订 |
| 阻塞等待时长持续偏高 | 提问**批量呈现**；非阻塞问题改走假设 | `ai-sdlc-decision-authority.mdc` §6 修订 |

### 4.2 校准不得用来绕过门禁

| 禁止 | 为什么 |
|---|---|
| ❌ 「这个任务例外，先放过」 | 校准的产物是**规则修订**，不是**单次豁免** |
| ❌ 为了让指标好看而降低门禁 | 指标是流程参数调整的**输入**，不是目标 |
| ❌ 校准时删掉指标 | 指标消失 = 观测能力消失，下次同样的问题还会发生 |

### 4.3 修订需要走流程

| 修订类型 | 路径 |
|---|---|
| 门禁严重度 | **RFC 修订**（七项 rubric 增删需 RFC；严重度降级也需 RFC） |
| 复杂度打分表 | 规则文件修订 + 记录理由 |
| CI 断言阈值 | 规则文件 / CI 配置修订 + 记录理由 |
| 指标口径 | 本文件修订 |

## 5. 审计留痕

**每个动作都必须产生不可变、可防篡改的审计条目。**

### 必填字段

| 字段 | 说明 |
|---|---|
| `actor` | 主体（人 / AI 代理 / 服务账号 / bot） |
| `action` | 做了什么 |
| `resource` | 作用对象（任务号 / 提交号 / PR 号） |
| `timestamp` | 何时（ISO 8601） |
| `decision` | 依据的决策 / 门禁判定 |
| `result` | 结果（pass / fail / overridden / escalated） |

### 本仓库的审计载体

| 事件 | 载体 |
|---|---|
| DoR 判定 | 任务文件的 `## DoR 判定` 段落 |
| 门禁执行 | CI 日志（每次 push 不可变） |
| 决策记录 | PR 描述或任务文件的 `## 决策记录` 段落 |
| Override | PR 描述必须写明：门禁名、授权人角色、理由 |
| 评审结论 | PR 评审记录 |
| 任务归档 | `git mv` 提交历史 |

### 不可变性

- 审计条目**一旦写入即不可变**。
- 更正通过**新增**条目完成，**不修改旧条目**。
- `main` 上的历史**不得重写**（线性历史，禁止 force push 到 `main`）。

### 留存与访问

| 类别 | 留存 | 访问 |
|---|---|---|
| 审计条目 | 长期（随仓库历史） | 全体贡献者 |
| 门禁执行日志 | 随 CI 产物 | 全体贡献者 |
| 指标快照 | 至少一个迭代周期 | 全体贡献者 |
| **凭据 / 密钥相关日志** | **不得留存** | — |

**审计条目不得包含任何凭据、密钥或个人信息。**

## 6. 服务侧可观测性（未接入）

上游 `spec/metrics.md` §3 要求 OpenTelemetry 集成（trace / metrics / logs）。
本仓库**流程侧**的审计已落地，**服务侧**的 OTel 尚未接入。

| 项 | 现状 |
|---|---|
| `trace_id` 贯穿 | ✅ 类型字段中（`rust-code-standards.mdc` §1：「可观测性是结构的一部分」）—— 不靠字符串拼接约定 |
| OTel exporter 配置 | ✅ `NX_OBSERVABILITY__OTLP_ENABLED` / `NX_OBSERVABILITY__OTLP_ENDPOINT` 已在映射表中 |
| 实际导出 | ⚠️ 待接入 |

**这不影响流程侧门禁** —— 门禁判据不依赖 OTel。
但它影响 S8 的「关键路径有指标与结构化日志」判据，见 `ai-sdlc-observability.mdc` §6。
