# DoR 门禁操作手册

> **判据在 `.cursor/rules/ai-sdlc-dor-gate.mdc`**。本手册讲**怎么执行**、**怎么写记录**、
> **不通过时怎么办**。两者冲突时以规则文件为准。

---

## 0. 什么时候跑这道门禁

**在任何代码写入之前**。

不是「打算写的时候」，是**准备写第一行代码的时候**。
本仓库有两道硬边界，S3→S4 是其中一道 —— 它防的是「交付了错误的东西」。

```
S1 分层判定 → S2 产出物编写 → S3 DoR 门禁 ══╗ 不通过 → 退回 S2
                                          ↓ 通过
                                        S4 实现
```

上游 AI-SDLC 由 `pipeline-cli` 的 `cli-dor-check.mjs` 自动执行（Stage A 脚本 + Stage B LLM）。
**本仓库未接入管道** —— 门禁**手工执行**，判定记录**落到任务文件里**。

---

## 1. Stage A：确定性检查（先跑，永远先跑）

Stage A 不依赖 LLM、可复现、<100ms。**Stage A 失败直接短路**，不发起 Stage B。

下面每一项都给出**可执行的检查方式**。用 `grep` / `wc` 就能做。

### A1 AC 可二元测试

| 检查 | 命令 |
|---|---|
| AC 条数在 1–20 之间 | `grep -cE '^- \[[ x]\] #[0-9]+' <task>.md` |
| 每条 AC 非空 | 检查 `- [ ] #N` 后面有非空文本 |
| 无「不可判定」的措辞 | `grep -inE '改善|提升|优化|更好|更可靠|感觉' <task>.md` —— 命中即人工复核 |

**通过判据**：AC 数量 1–20，且每条都能写成「5 分钟内可判定的通过/失败检查」。

**常见失败**：
- ❌ 「改善用户体验」→ 不可判定
- ❌ 「按架构文档实现」→ 没指名具体条款与行为
- ✅ 「`nexus-llm` 的 `Cargo.toml` 不依赖 `nexus-repo`」→ 可执行（`grep` 一下）

### A2 正文无未决标记

```bash
grep -nEi '\b(TBD|TODO|XXX|FIXME|\?\?\?)\b' <task>.md
grep -nEi "not sure|we'll figure out|decide later|up to the dev|待定|后面再定" <task>.md
```

**通过判据**：两条命令都无输出。

> **注意**：本条**完全确定性** —— 没有 Stage B 环节。

**常见失败**：作者留了占位符打算以后填。**禁止**用「先写着，回头补」绕过。

### A3 引用可解析

| 引用类型 | 检查 |
|---|---|
| 仓库路径 | 路径真实存在（`docs/architecture/...`、`crates/...`、`scripts/...`） |
| 章节号 `#NN` | 目标文档里确实有该章节 |
| 任务号 `NEX-nn` | `backlog/tasks/` 或 `backlog/completed/` 下有该任务文件 |
| RFC 号 | `docs/rfcs/` 下有该 RFC 文件，或任务文件的 `references` 里指向上游 RFC |

**通过判据**：每条指名的引用都能唯一解析到具体位置。

**常见失败**：
- ❌ 「像 dashboard 那个 PR」→ 无链接，裸引用
- ❌ 「§5.3」但架构文档里没有 §5.3 → 章节号漂移

### A5 受影响面被指名

```bash
grep -nE '`[a-z-]+/[A-Za-z0-9._/-]+`' <task>.md   # 文件路径
grep -nE '(nexus-[a-z]+|crates/)' <task>.md       # crate / 组件
```

**通过判据**：明确指出了改哪些文件 / crate / 系统组件 / 路由 / 界面。

**常见失败**：
- ❌ 「慢查询」→ 没点名库、表、负载
- ❌ 「改进 LLM 层」→ 指名了 crate 但没指名文件范围

### A7 无隐形依赖

```bash
grep -nEi 'requires|depends on|after .* ships|等 .* 完成' <task>.md
```

每一条命中都要能对应到：

- `backlog/completed/` 下的已完成任务，**或**
- `backlog/tasks/` 下已登记的任务，或
- frontmatter 的 `dependencies` 字段里的 `NEX-nn`

**通过判据**：没有「未言明的结构性假设」。

**常见失败**：❌ 「等 auth 重写完」但仓库里没有 auth 重写的任务文件。

## 2. Stage B：语义判定（仅在 Stage A 全过后）

Stage B 回答的是**正则判不了**的问题。每项都是**是 / 否**。

| 门禁 | Stage B 的问题 | 判「否」意味着 |
|---|---|---|
| 1 | 「每条 AC 真的是二元可判定的吗？」 | AC 只是看起来具体，实际要人肉判断 |
| 4 | 「这落在一个合理的 PR 内吗？」 | 范围超过单个 PR 的 diff 规模 |
| 5 | 「这个面指得够具体吗？」 | 指名了组件但没说清改哪几处 |
| 6 | 「用户可见的终态能一句话说清吗？」 | 只描述了问题，没有终态 |
| 7 | 「有没有未言明的结构性假设？」 | 依赖没说清，但被别处提及 |

### Stage B 的自问模板

对每条 Stage B 门禁，**逐字回答**下面三问，答案写进判定记录：

1. **我具体在问什么？**（把抽象门禁换成一个具体问题）
2. **答案是什么？**（是 / 否，不许「基本是」）
3. **依据是什么？**（指到任务的哪一段）

示例（门禁 6）：

> 1. 「上线后使用者能 ___ 什么？」—— 完成态是什么？
> 2. 否 —— 任务只说「让重试更稳」，没说调用方能观察到的不变。
> 3. 「## Description」第二段只描述了问题，没有终态描述。

## 3. 判定记录模板

**必须落到任务文件里**，否则下次接手的人无法复核。

```markdown
## DoR 判定

- 门禁 1（AC 可二元测试）：通过 —— 11 条 AC，均可写成命令或断言
- 门禁 2（无未决标记）：通过
- 门禁 3（引用可解析）：通过 —— §2.6.3、§3.1.1 均存在于架构文档
- 门禁 4（范围有界）：通过 —— 单 crate 改动，无跨 crate 契约变更
- 门禁 5（受影响面被指名）：通过 —— `crates/nexus-llm/src/**`
- 门禁 6（完成态可描述）：通过 —— 调用方可以用 `bound_chat_descriptor` 在本地裁剪预算
- 门禁 7（无隐形依赖）：通过 —— NEX-16 已完成

**结论：pass**
```

### 结论只有三种

| 结论 | 何时用 | 下一步 |
|---|---|---|
| `pass` | 七项全过 | 开工（S4） |
| `needs-clarification` | 门禁 1/2/3/5/7 失败 | **退回 S2 澄清，不写代码** |
| `blocked` | 被上游任务或未决 OQ 阻塞 | 登记依赖，等上游 |

### 记录的三条纪律

1. **逐项点名**，不写「整体看起来可以」。七项缺一不可。
2. **失败项写清「建议的改法」** —— 指名，不泛泛说「不够清晰」。
3. **结论与记录一致** —— 记录里有一项「不通过」而结论写 `pass`，是**纪律事故**。

## 4. 澄清回路：不通过时怎么办

```
门禁不通过
   │
   ├─ 1. 任务 status 置为 `Needs Clarification`
   │
   ├─ 2. 写清哪几项失败 + 建议的改法（指名）
   │
   ├─ 3. 停下 —— 不写代码
   │
   └─ 4. 补齐后重跑门禁
```

### 禁止的短路

| 禁止 | 为什么 |
|---|---|
| ❌ 把 AC 改成不可判定来「骗过」门禁 | 门禁是**质量边界**，不是**形式检查** |
| ❌ 在实现里隐式解决 OQ | 代码「顺手」定了某件事 = 代理消解了只有操作者能解的问题 |
| ❌ 用「先写着，回头补」绕过门禁 2 | 门禁 2 抓的是「作者留了占位符打算以后填」这个失效模式本身 |
| ❌ 降级严重度来通过 | 严重度是**门禁的属性**，不是任务的属性；代理对某次失败**无裁量权** |

---

## 5. 谁来解决未决问题

门禁 1–7 失败时，**澄清的责任在作者**（人或代理），代理可以自行修。

但**如果澄清需要一个决策**（比如「这个超时该算可重试还是结果未知」），
那就是**架构文档已定稿条款**或 **OQ** —— 走
`.cursor/rules/ai-sdlc-decision-authority.mdc` §4 的升级流程，**不得在任务文件里顺手决定**。

**Away rule**：操作者不在场时不发起阻塞性提问。
非阻塞性问题按假设推进并**把假设显式写出来** —— 沉默的假设是最贵的假设。

## 6. 自检清单

开工前逐条打勾：

- [ ] AC 数量在 1–20 之间？
- [ ] 每条 AC 都能写成「5 分钟内判定通过/失败」的检查？
- [ ] 正文里没有 `TBD` / `TODO` / `FIXME` / `???`？
- [ ] 每条引用都能解析到具体位置？
- [ ] 范围落在一个 PR 内？
- [ ] 指名了要改的文件 / crate / 组件？
- [ ] 能一句话说出「上线后使用者能 ___」？
- [ ] 没有未言明的结构性假设？
- [ ] 判定记录已写进任务文件？
- [ ] 结论与记录一致？
