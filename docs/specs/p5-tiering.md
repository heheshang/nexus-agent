## 判定：Tier 2 · Spec

### 不是 Tier 1 · RFC —— 主干已定稿

逐项检查 P5 的技术选择：

| 技术选择 | 会不会有分歧 | 依据 |
|---|---|---|
| SSE 输出用 `Body::from_stream` 还是 axum 的 `Sse` | ❌ **不会** | 参考架构 §1.5 **已定稿**：「建议手写 `Body::from_stream`，保持字节级一致，避免前端兼容问题」 |
| SSE 帧格式（`event: / data: / 空行`） | ❌ 不会 | 参考架构 §1.5 **已定稿**，且 `examples/demo-sse-frames` 已有回归基准 |
| 事件名映射（`EventPayload` → SSE `event:`） | ❌ 不会 | 架构文档 §2.2.4.1 的 **12 个事件名已定稿**，且 `nexus-core` 的 `EventPayload` 已实现 |
| 半帧处理策略 | ❌ 不会 | 参考架构 §1.5 + 附录 C.1 **已定稿**（「必须把分隔符一起切走」） |
| REST 响应包形状 | ❌ 不会 | 参考实现的 `internal/pkg/response` **已定稿**，架构文档 §2.6.5 的 `UserFacing` 形状也**已定稿** |
| 鉴权中间件的归属 | ❌ 不会 | 参考架构 §0.3 的 crate 职责表**已定稿**：`nexus-api` 做「鉴权与门禁中间件」，**归属校验在 service** |

**结论**：P5 的**主干**（SSE 帧编解码、桥接、错误响应、中间件骨架）
在参考架构与架构文档里**已经定稿**，不构成 RFC 级分歧。

> **注意**：其中两项**在开工前**就由操作者明确选定了
> （见 §「操作者已作出的决策」），进一步确认了不构成 RFC 级分歧。

### 是 Tier 2 · Spec —— 不是 Task 层

P5 **明显**能拆成多个可独立评审的任务：

| 子能力 | 可独立评审 | 依赖 |
|---|---|---|
| SSE 帧编解码器（半帧缓冲） | ✅ | 无 |
| 事件 → SSE 桥接（`Body::from_stream`） | ✅ | 帧编解码器 |
| 协议层中间件（鉴权上下文、错误兜底） | ✅ | 无 |
| 路由骨架与装配 | ✅ | 桥接 + 中间件 |
| 收口（架构文档同步 + 契约升格） | ✅ | 全部 |

每个子能力都有**独立的**可二元测试的验收条件，
且**互不阻塞**（除了显式的依赖顺序）。

按 `ai-sdlc-workflow.mdc` §3 ——「一个特性能拆成多个任务 → 升到 Spec」。

## 操作者已作出的决策（开工前）

### 决策 A —— SSE 输出**手写** `Body::from_stream`

| 项 | 内容 |
|---|---|
| **类别** | (a) decide-and-proceed |
| **决策** | P5 的 SSE 输出**手写** `Body::from_stream`，**不用** axum 的 `Sse` 类型 |
| **依据** | 参考架构 §1.5 已定稿：axum 的 `Sse` 会用 `Event::default().data()` **自动转义** data，与 Go 版手写 `event:` / `data:` 的字节输出**不完全一致** —— 前端 `lib/sse.ts` 是按字节解析的 |
| **可逆性** | 高 —— 换回 axum 的 `Sse` 是局部改动；但那会**破坏**前端兼容性，所以实际不可逆 |
| **影响面** | `crates/nexus-api/src/sse.rs`（帧编解码）+ `crates/nexus-api/src/bridge.rs`（桥接） |

### 决策 B —— P5 的交付边界是**传输层能力**，不是完整 chat 端点

| 项 | 内容 |
|---|---|
| **类别** | (a) decide-and-proceed |
| **决策** | P5 交付：**SSE 帧编解码 + 桥接 + 中间件 + 路由骨架**，用 **trait 接缝**连接上层；**不做**业务编排 |
| **依据** | ① `nexus-service` 是 7 行空壳 —— 做完整 chat 端点就等于**同时**填 `nexus-service`（跨 crate 的会话编排、归属校验、上下文组装），那是**另一个阶段**的工作量；② 架构文档 §1.4 的能力分层：**协议层能感知 HTTP / SSE 语义与已认证的身份，但不能感知业务规则、事务边界** —— 业务编排**本来就不该**在 `nexus-api`；③ 「不扩大范围」 |
| **可逆性** | 高 —— trait 接缝是**接口**，后续填 `nexus-service` 实现**不改** `nexus-api` |
| **影响面** | `crates/nexus-api/src/*`；**不新增** crate 依赖方向 |

> **决策 B 的关键后果**：`nexus-api` **不得**依赖 `nexus-service` 的**具体实现** ——
> 它依赖的是**trait**（消费方定义 trait 模式，参考架构 §0.4 的 `RouterChat` 同构）。
> 这与 `nexus-agent` 对 `nexus-llm` 的处理（D4）是**同一条纪律**。

## 登记的开放问题

### OQ-1 —— `FinishReason` 是否需要 `Canceled` 变体？

**性质**：**非阻塞性**。

P4 的 Spec §6.3 登记了后续任务 **F2**：

> `FinishReason` 增加 `Canceled` 变体 —— 当**协议层**（P5，`nexus-api` 的 SSE 桥接）
> 需要**向前端区分**「用户取消」与「正常结束」时。

**P5 正是那个触发条件已到的阶段。**

但**本阶段不解决它**，理由：

1. `FinishReason` 属于**事件契约**（架构文档 §6.3 已定稿的 12 个事件负载）。
   改它 = **协议破坏性变更**，需要前后端同步。
2. P5 当前的**交付边界**（决策 B）**不需要**区分取消 ——
   取消在 P4 已经用 `done` + `FinishReason::Stop` 表达，
   事实由 `RequestStatus::Canceled` 指标承载。
3. 按「不扩大范围」，P5 只**登记**该问题，**不在实现里顺手决定**。

**处置**：在 P5 的 Spec §6.3 登记为 F3（承接 P4 的 F2），
并在**收口任务**（T-006）里核对「是否已有前端需求触发」。

### OQ-2 —— REST 端点的**具体集合**与鉴权要求

**性质**：**非阻塞性**。

P5 交付**路由骨架**（决策 B），但**哪些** REST 端点、每个端点**是否**要求鉴权，
取决于业务需求 —— 而业务端点的**集合**要到 P6/P7/P8 才有内容。

**处置**：
- P5 交付**路由骨架 + 装配机制**（可注册路由的 `Router` 构建器），
  以及**两个**具体端点：`/metrics`（NEX-25 已交付）与**一个**示范性的 SSE 端点。
- 其余端点随对应阶段增量注册。
- 鉴权的**机制**（中间件形态、如何提取身份）由 P5 交付，
  但**哪些**端点挂它**逐端点决定**。

## 复杂度打分（`ai-sdlc-autonomy.mdc` §2.1）

| 维度 | 分数 | 依据 |
|---|---|---|
| 契约影响 | **4** | SSE `event:` 名与帧格式是**前后端契约**（但事件名**已定稿**，P5 只是**搬运**） |
| 依赖面 | **4** | 单 crate（`nexus-api`）内部；**不新增** crate 依赖方向 |
| 可逆性 | **2** | 纯新增代码，易回滚 |
| 探索性 | **3** | 帧编解码有 `examples/demo-sse-frames` 作回归基准，路径确定 |
| 并发/一致性 | **3** | 桥接涉及流与取消，但**不涉及**分布式一致 |

**取最高分 = 4** → 中等复杂度 → 路由策略 **`ai-with-review`**（**默认**）。

**不满足** `fully-autonomous` 的两个前提中的「低复杂度」——
所以**默认走人工评审**，不做完全自治。
