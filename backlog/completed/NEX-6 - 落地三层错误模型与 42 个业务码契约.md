## Description

架构文档 §6.1 的 **P1 核心类型**第三部分：把 §2.6 的三层错误模型与 §2.6.4.1 的 42 个业务码搬进 `nexus-core`。

### 三层错误（§2.6.1）

| 层 | 类型 | 谁处理 |
|---|---|---|
| 领域错误 | 各领域的 enum（`thiserror`） | 领域内部 |
| 应用错误 | `AppError` | 用例层 → 协议层 |
| 传输错误 | `axum` 的 `IntoResponse` | 协议层（**P5，不在本任务**） |

### 失败分类是第一公民（§2.6.3）

```rust
pub enum RetryPolicy {
    Retryable,      // 明确失败，重试安全
    UnknownOutcome, // 结果未知，重试可能产生重复副作用
    Terminal,       // 明确失败，重试无意义
}
```

**`UnknownOutcome` 是本设计相对参考实现的关键改进**：参考实现的 `IsRetryable` 把 504（超时）与 502（明确不可用）一视同仁，但 504 意味着上游**可能已经执行了副作用** —— 支付类工具在 504 下重试会重复扣费。

### 内部原因绝不外泄（§2.6.5）

```rust
pub struct UserFacing {
    pub code: ErrorCode,
    pub message: Cow<'static, str>,
}

pub struct AppError {
    pub facing: UserFacing,
    pub cause: Option<Arc<dyn Error + Send + Sync>>,  // 只进日志，绝不序列化
}
```

`UserFacing` 在**类型上**就无法携带内部原因。

### §2.6.4.1 业务码表（定稿，42 个）

码段沿用参考实现：1=参数 2=认证 3=会话 4=限流 5=LLM 6=RAG 7=工具 8=协议 9=系统。

**两处「看着像笔误」的地方是参考实现的原样，必须原样保留**：
- 码段 6 从 `60002` 起（没有 `60001`）
- 码段 9 的 `90002` 在 `90003` 之前

改号会让已上线的前端分支逻辑失效。

**`ErrorCode` 必须手工实现 `Serialize`** —— derive 会输出变体名 `"ModelTimeout"` 而不是数字码 `50002`，那会破坏「前端按码段通用处理」的语义（附录 C.1 陷阱）。

### 依赖

需要 NEX-4 的 `ErrorCode` 引用 ID 类型吗？不需要 —— 但 `AppError` 的 `Error` 变体里若有 ID，需要。

## 备注

- 「传输错误层（`axum` 的 `IntoResponse`）」属于 **P5 协议层**，不在本任务 —— `nexus-core` 不依赖 `axum`。
- 架构文档未明确 `AppError` 是否需要 `From<ModelError>` 这类具体领域错误转换。本任务只落地 `ModelError` 作为**示例**，具体领域的错误 enum 随各 crate 落地时再定 —— 但转换的**模式**（`#[from]` + 穷尽 `match`）必须由示例确立。
- `AppError` **刻意不实现 `Serialize`** —— 要输出给客户端只能给 `UserFacing`。这是 §2.6.5「内部原因绝不外泄」的最强形态：不是「约定不序列化」，而是「编译不了」。

## 实现过程中的发现

**1. `AppError` 不实现 `Serialize`，而不是「实现了但只序列化 facing」。**
架构文档 §2.6.5 写的是「`cause` 绝不序列化」。若给 `AppError` 实现 `Serialize` 并跳过 cause，
就留下了「有人改成派生 `Serialize` 就泄露」的路。**不实现**从类型上消灭了这条路 ——
由负向测试 `app_error_is_not_serializable`（E0277）固化。

**2. `retry_policy` 挂在 `ErrorCode` 上，不只挂在 `AppError` 上。**
失败分类是**码的属性**，不是错误的属性 —— 同一个码在任何上下文里分类都相同。
挂在 `ErrorCode` 上让 `ErrorCode::retry_policy()` 可直接用（如「这个码能不能自动重试」，
不需要先构造一个 `AppError`）。`AppError::retry_policy()` 委托给它。

**3. `retry_policy` 用**穷尽匹配**而非 `_ =>` 兜底。**
新增错误码时编译器强制要求分类 —— 不会静默落进某个默认分支。
这是「失败分类是第一公民」（§2.6.3）的实质：分类不是可选项。

**4. 契约测试的有效性用**变异测试**验证过。**
「测试通过」不等于「测试能失败」。注入两处变异确认契约测试真的会红：
- 把 `ModelTimeout` 从 `UnknownOutcome` 改到 `Retryable` → 4 个测试失败
  （正是架构文档警告的「504 下重试会重复扣费」那个回归）
- 把 `ParseFailed` 从 `60002` 改成 `60001` → 3 个测试失败
  （正是「码段 6 从 60002 起」那个「看着像笔误」的地方）
两处变异均已还原。

**5. `Deserialize` 也必须手工实现。**
架构文档只强调了 `Serialize` 必须手工（否则输出变体名）。但对称地，
`Deserialize` 若派生会期望变体名 `"ModelTimeout"` —— 与序列化的数字形状不匹配。
本任务手工实现成读数字码，未知码值返回错误。
